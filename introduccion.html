    1. Introducción

    El PDF de este documento está disponible |AQUÍ|.

    Los ejemplos de este documento están disponibles |AQUÍ|.

    En este documento, nuestro objetivo es presentar, a través de ejemplos, los conceptos clave de Spring MVC, un marco web de Java que proporciona un entorno para desarrollar aplicaciones web según el patrón MVC (Modelo-Vista-Controlador). Spring MVC es una rama del ecosistema Spring [http://projects.spring.io/spring-framework/]. También presentamos el motor de vistas Thymeleaf [http://www.thymeleaf.org/].

    Este curso está dirigido a lectores con un dominio sólido del lenguaje Java. No se requieren conocimientos previos de programación web.

    Aunque es detallado, es probable que este documento esté incompleto. Spring es un marco de trabajo muy amplio con muchas ramas. Para obtener más información sobre Spring MVC, puede consultar los siguientes recursos:

    • el documento de referencia del marco Spring [http://docs.spring.io/spring/docs/current/spring-framework-reference/pdf/spring-framework-reference.pdf];
    • numerosos tutoriales de Spring disponibles en [http://spring.io/guides]
    • el sitio [developpez.com] dedicado a Spring [http://spring.developpez.com/].

    Este documento se ha redactado de manera que pueda leerse sin necesidad de tener un ordenador a mano. Por ello, se incluyen numerosas capturas de pantalla.

    1.4. El papel de Spring MVC en una aplicación web

    Situemos Spring MVC en el contexto del desarrollo de una aplicación web. En la mayoría de los casos, se basará en una arquitectura de varios niveles como la siguiente:

    • la capa [Web] es la capa que está en contacto con el usuario de la aplicación web. El usuario interactúa con la aplicación web a través de páginas web que se visualizan en un navegador. Spring MVC se encuentra en esta capa y solo en esta capa;
    • la capa [de negocio] implementa la lógica de negocio de la aplicación, como el cálculo de un salario o una factura. Esta capa utiliza datos del usuario a través de la capa [Web] y del SGBD a través de la capa [DAO];
    • la capa [DAO] (objetos de acceso a datos), la capa [ORM] (mapeador relacional de objetos) y el controlador JDBC gestionan el acceso a los datos en el SGBD. La capa [ORM] actúa como puente entre los objetos gestionados por la capa [DAO] y las filas y columnas de las tablas de una base de datos relacional. Aquí utilizaremos el ORM Hibernate. Una especificación denominada JPA (Java Persistence API) nos permite abstraernos del ORM específico utilizado, siempre que este implemente dichas especificaciones. Este es el caso de Hibernate y otros ORM de Java. Por lo tanto, en adelante nos referiremos a la capa ORM como la capa JPA;
    • la integración de las capas la gestiona el marco Spring;

    La mayoría de los ejemplos que se proporcionan a continuación utilizarán solo una única capa, la capa [Web]:

    Sin embargo, este documento concluirá con la creación de una aplicación web de varios niveles:

    El navegador se conectará a una aplicación [Web1] implementada con Spring MVC / Thymeleaf, que recuperará sus datos de un servicio web [Web2] también implementado con Spring MVC. Esta segunda aplicación web accederá a una base de datos.

    1.5. El modelo de desarrollo de Spring MVC

    Spring MVC implementa el patrón arquitectónico MVC (Modelo-Vista-Controlador) de la siguiente manera:

    El procesamiento de una solicitud del cliente se lleva a cabo de la siguiente manera:

    1. solicitud: las URL solicitadas tienen el formato http://machine:port/contexte/Action/param1/param2/....?p1=v1&p2=v2&... El [Front Controller] utiliza un archivo de configuración o anotaciones Java para «enrutar» la solicitud al controlador correcto y a la acción correcta dentro de ese controlador. Para ello, utiliza el campo [Action] de la URL. El resto de la URL [/param1/param2/...] consta de parámetros opcionales que se pasarán a la acción. La C de MVC se refiere aquí a la cadena [Front Controller, Controller, Action]. Si ningún controlador puede gestionar la acción solicitada, el servidor web responderá que no se ha encontrado la URL solicitada.
    2. procesamiento
    • La acción seleccionada puede utilizar los parámetros que le ha pasado el [Front Controller]. Estos pueden proceder de varias fuentes:
      • la ruta [/param1/param2/...] de la URL,
      • los parámetros [p1=v1&p2=v2] de la URL,
      • de los parámetros enviados por el navegador con su solicitud;
    • al procesar la solicitud del usuario, la acción puede necesitar la capa [business] [2b]. Una vez procesada la solicitud del cliente, puede desencadenar diversas respuestas. Un ejemplo clásico es:
      • una página de error si la solicitud no se ha podido procesar correctamente
      • una página de confirmación en caso contrario
    • La acción indica a una vista específica que se renderice [3]. Esta vista mostrará los datos conocidos como el modelo de vista. Esta es la «M» de MVC. La acción creará este modelo de vista [2c] e indicará a una vista que se renderice [3];
    1. Respuesta: la vista seleccionada V utiliza el modelo M construido por la acción para inicializar las partes dinámicas de la respuesta HTML que debe enviar al cliente y, a continuación, envía esta respuesta.

    Ahora, aclaremos la relación entre la arquitectura web MVC y la arquitectura por capas. Dependiendo de cómo definamos el modelo, estos dos conceptos pueden estar relacionados o no. Consideremos una aplicación web Spring MVC de una sola capa:

    Si implementamos la capa [Web] con Spring MVC, tendremos efectivamente una arquitectura web MVC, pero no una arquitectura en capas. En este caso, la capa [Web] se encargará de todo: la presentación, la lógica de negocio y el acceso a los datos. Son las acciones las que realizarán este trabajo.

    Ahora, consideremos una arquitectura web multicapa:

    La capa [Web] se puede implementar sin un marco de trabajo y sin seguir el modelo MVC. Entonces tenemos una arquitectura de varias capas, pero la capa Web no implementa el modelo MVC.

    Por ejemplo, en el entorno .NET, la capa [Web] anterior se puede implementar con ASP.NET MVC, lo que da como resultado una arquitectura en capas con una capa [Web] de estilo MVC. Una vez hecho esto, podemos sustituir esta capa ASP.NET MVC por una capa ASP.NET clásica (WebForms) sin modificar el resto (lógica de negocio, DAO, ORM). De este modo, obtenemos una arquitectura en capas con una capa [Web] que ya no se basa en MVC.

    En MVC, dijimos que el modelo M era el de la vista V, es decir, el conjunto de datos mostrados por la vista V. Se ofrece otra definición del modelo M en MVC:

    Muchos autores consideran que lo que se encuentra a la derecha de la capa [Web] constituye el modelo M de MVC. Para evitar ambigüedades, podemos referirnos a:

    • el modelo de dominio cuando nos referimos a todo lo que se encuentra a la derecha de la capa [Web]
    • el modelo de vista cuando nos refiramos a los datos mostrados por una vista V

    En lo sucesivo, el término «modelo M» se referirá exclusivamente al modelo de una vista V.

    1.6.3. La arquitectura de una aplicación Spring MVC

    Spring MVC implementa el patrón arquitectónico MVC (Modelo-Vista-Controlador):

    El procesamiento de una solicitud del cliente se lleva a cabo de la siguiente manera:

    1. solicitud: las URL solicitadas tienen el formato http://machine:port/contexte/Action/param1/param2/....?p1=v1&p2=v2&... El [Dispatcher Servlet] es la clase de Spring que gestiona las URL entrantes. «Enruta» la URL a la acción que debe gestionarla. Estas acciones son métodos de clases específicas denominadas [Controladores]. La C de MVC aquí es la cadena [Servlet Dispatcher, Controlador, Acción]. Si no se ha configurado ninguna acción para gestionar la URL entrante, el [Servlet Dispatcher] responderá que no se ha encontrado la URL solicitada (error 404 NOT FOUND);
    2. el procesamiento
    • la acción seleccionada puede utilizar los parámetros que el [Servlet Dispatcher] le ha pasado. Estos pueden provenir de varias fuentes:
      • la ruta [/param1/param2/...] de la URL,
      • los parámetros de la URL [p1=v1&p2=v2],
      • de los parámetros enviados por el navegador con su solicitud;
    • al procesar la solicitud del usuario, la acción puede necesitar la capa [de negocio] [2b]. Una vez procesada la solicitud del cliente, esta puede desencadenar diversas respuestas. Un ejemplo clásico es:
      • una página de error si la solicitud no se ha podido procesar correctamente
      • una página de confirmación en caso contrario
    • la acción indica que se muestre una vista específica [3]. Esta vista mostrará datos conocidos como el modelo de vista. Esta es la M de MVC. La acción creará este modelo M [2c] e indicará que se muestre una vista V [3];
    1. respuesta: la vista V seleccionada utiliza el modelo M construido por la acción para inicializar las partes dinámicas de la respuesta HTML que debe enviar al cliente y, a continuación, envía esta respuesta.

    Examinaremos estos diferentes elementos en el proyecto que estamos estudiando.

    1.6.4. El controlador C

      

    La aplicación importada tiene el siguiente controlador:

    
package hello;
 
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
 
@Controller
public class GreetingController {
 
    @RequestMapping("/greeting")
    public String greeting(@RequestParam(value="name", required=false, defaultValue="World") String name, Model model) {
        model.addAttribute("name", name);
        return "greeting";
    }
 
}
    • línea 8: la anotación [@Controller] convierte a la clase [GreetingController] en un controlador de Spring, lo que significa que sus métodos se registran para gestionar URL. Un controlador de Spring es un singleton. Solo se crea una única instancia;
    • línea 11: la anotación [@RequestMapping] especifica la URL gestionada por el método, en este caso la URL [/greeting]. Más adelante veremos que esta URL se puede parametrizar y que es posible recuperar estos parámetros;
    • línea 12: el método acepta dos parámetros:
      • [String name]: este parámetro se inicializa con un parámetro llamado [name] en la solicitud procesada, por ejemplo [/greeting?name=alfonse]. Este parámetro es opcional [required=false] y, cuando no está presente, el parámetro [name] tomará el valor «World» [defaultValue="World"],
      • [Model model] es un modelo de vista. Se pasa vacío, y es función de la acción (el método greeting) rellenarlo. Este modelo se pasará a la vista que renderizará la acción. Por lo tanto, es un modelo de vista;
    • línea 13: el valor de [name] se coloca en el modelo de vista. La clase [Model] se comporta como un diccionario;
    • línea 14: el método devuelve el nombre de la vista que debe mostrar el modelo construido. El nombre exacto de la vista depende de la configuración de [Thymeleaf]. A falta de dicha configuración, la vista mostrada aquí será [/templates/greeting.html], donde la carpeta [templates] debe estar en la raíz de la ruta de clases del proyecto;

    Examinemos nuestro proyecto de Eclipse:

    Las carpetas [src/main/java] y [src/main/resources] son carpetas cuyo contenido se añadirá a la ruta de clases del proyecto. En [src/main/java] se colocarán las versiones compiladas del código fuente Java. El contenido de la carpeta [src/main/resources] se añade a la ruta de clases sin modificaciones. Por lo tanto, podemos ver que la carpeta [templates] estará en la ruta de clases del proyecto [1].

    Puede verificarlo [2-3] en la ventana [Navigator] de Eclipse [Window / Show view / Other / General / Navigator]. La carpeta [target] se crea al compilar (o «construir») el proyecto. La carpeta [classes] representa la raíz de la ruta de clases. Puede ver que la carpeta [templates] está presente allí.

    1.6.5. La vista V

    En MVC, acabamos de ver el controlador C y el modelo M. La vista V está representada aquí por el siguiente archivo [greeting.html]:

    
<!DOCTYPE HTML>
<html xmlns:th="http://www.thymeleaf.org">
<head>
<title>Getting Started: Serving Web Content</title>
<meta http-equiv="Content-Type" content="text/html; charset=UTF-8" />
</head>
<body>
    <p th:text="'Hello, ' + ${name} + '!'" />
</body>
</html>
    • línea 2: el espacio de nombres de etiquetas de Thymeleaf;
    • línea 8: una etiqueta <p> (párrafo) con un atributo de Thymeleaf. El atributo [th:text] establece el contenido del párrafo. Dentro de la cadena, tenemos la expresión [${name}]. Esto significa que queremos el valor del atributo [name] de la plantilla de vista. Ahora, recuerda que este atributo fue añadido al modelo por la acción: 
    
model.addAttribute("name", name);

    El primer parámetro establece el nombre del atributo y el segundo establece su valor.

    1.6.6. Ejecución

      

    La clase [Application.java] es la clase ejecutable del proyecto. Su código es el siguiente:

    
package hello;
 
import org.springframework.boot.autoconfigure.EnableAutoConfiguration;
import org.springframework.boot.SpringApplication;
import org.springframework.context.annotation.ComponentScan;
 
@ComponentScan
@EnableAutoConfiguration
public class Application {
 
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
 
}
    • Línea 11: La clase es ejecutable con un método [main] específico para aplicaciones de consola. La clase [SpringApplication] de la línea 12 iniciará el servidor Tomcat presente en las dependencias e implementará el servicio web en él;
    • línea 4: podemos ver que la clase [SpringApplication] pertenece al proyecto [Spring Boot];
    • línea 12: el primer parámetro es la clase que configura el proyecto, el segundo contiene cualquier parámetro adicional;
    • línea 8: la anotación [@EnableAutoConfiguration] indica a Spring Boot que configure el proyecto;
    • línea 7: la anotación [@ComponentScan] hace que se escanee el directorio que contiene la clase [Application] en busca de componentes de Spring. Se encontrará uno: la clase [GreetingController], que tiene la anotación [@Controller], lo que la convierte en un componente de Spring;

    1.7.3. La arquitectura de un servicio Spring [web / JSON]

    Repasemos cómo Spring MVC implementa el modelo MVC:

    El procesamiento de una solicitud de un cliente se lleva a cabo de la siguiente manera:

    1. solicitud: las URL solicitadas tienen el formato http://machine:port/contexte/Action/param1/param2/....?p1=v1&p2=v2&... El [Dispatcher Servlet] es la clase de Spring que gestiona las URL entrantes. Este «enruta» la URL a la acción que debe procesarla. Estas acciones son métodos de clases específicas denominadas [Controladores]. La C de MVC aquí es la cadena [Servlet Dispatcher, Controlador, Acción]. Si no se ha configurado ninguna acción para gestionar la URL entrante, el [Servlet Dispatcher] responderá que no se ha encontrado la URL solicitada (error 404 NOT FOUND);
    2. el procesamiento
    • la acción seleccionada puede utilizar los parámetros que el [Servlet Dispatcher] le ha pasado. Estos pueden provenir de varias fuentes:
      • la ruta [/param1/param2/...] de la URL,
      • los parámetros de la URL [p1=v1&p2=v2],
      • de los parámetros enviados por el navegador con su solicitud;
    • al procesar la solicitud del usuario, la acción puede necesitar la capa [de negocio] [2b]. Una vez procesada la solicitud del cliente, esta puede desencadenar diversas respuestas. Un ejemplo clásico es:
      • una página de error si la solicitud no se ha podido procesar correctamente
      • una página de confirmación en caso contrario
    • la acción indica a una vista específica que se renderice [3]. Esta vista mostrará datos conocidos como el modelo de vista. Esta es la M de MVC. La acción creará este modelo M [2c] e indicará a una vista V que se renderice [3];
    1. Respuesta: la vista V seleccionada utiliza el modelo M creado por la acción para inicializar las partes dinámicas de la respuesta HTML que debe enviar al cliente y, a continuación, envía esta respuesta.

    En el caso de un servicio web / JSON, la arquitectura anterior se modifica ligeramente:

    • en [4a], el modelo, que es una clase Java, se convierte en una cadena JSON mediante una biblioteca JSON;
    • en [4b], esta cadena JSON se envía al navegador;

    1.7.4. El controlador C

      

    La aplicación importada tiene el siguiente controlador:

    
package hello;
 
import java.util.concurrent.atomic.AtomicLong;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
 
@RestController
public class GreetingController {
 
    private static final String template = "Hello, %s!";
    private final AtomicLong counter = new AtomicLong();
 
    @RequestMapping("/greeting")
    public Greeting greeting(@RequestParam(value = "name", defaultValue = "World") String name) {
        return new Greeting(counter.incrementAndGet(), String.format(template, name));
    }
}
    • Línea 9: La anotación [@RestController] convierte a la clase [GreetingController] en un controlador Spring, lo que significa que sus métodos se registran para gestionar URL. Ya hemos visto la anotación similar [@Controller]. El tipo de retorno de los métodos de ese controlador era [String], que era el nombre de la vista que se iba a mostrar. Aquí es diferente. Los métodos de un [@RestController] devuelven objetos que se serializan para enviarlos al navegador. El tipo de serialización que se realiza depende de la configuración de Spring MVC. Aquí, se serializarán a JSON. Es la presencia de una biblioteca JSON en las dependencias del proyecto lo que hace que Spring Boot configure automáticamente el proyecto de esta manera;
    • línea 14: la anotación [@RequestMapping] especifica la URL gestionada por el método, en este caso la URL [/greeting];
    • línea 15: ya hemos explicado la anotación [@RequestParam]. El resultado devuelto por el método es un objeto de tipo [Greeting].
    • línea 12: un entero largo de tipo atómico. Esto significa que admite el acceso concurrente. Es posible que varios subprocesos quieran incrementar la variable [counter] al mismo tiempo. Esto se gestionará correctamente. Un subproceso solo puede leer el valor del contador una vez que el subproceso que lo está modificando haya finalizado su modificación.

    1.7.5. El modelo M

    El modelo M generado por el método anterior es el siguiente objeto [Greeting]:

      
    
package hello;
 
public class Greeting {
 
    private final long id;
    private final String content;
 
    public Greeting(long id, String content) {
        this.id = id;
        this.content = content;
    }
 
    public long getId() {
        return id;
    }
 
    public String getContent() {
        return content;
    }
}

    Al convertir este objeto a JSON se creará la cadena {"id":n,"content":"text"}. En definitiva, la cadena JSON generada por el método del controlador tendrá el siguiente formato:

    {"id":2,"content":"¡Hola, mundo!"}

    o

    {"id":2,"content":"¡Hola, John!"}

    1.8. Conclusión

    Hemos presentado dos tipos de proyectos Spring MVC:

    • un proyecto en el que la aplicación web envía un flujo HTML al navegador. Este flujo es generado por el motor de vistas [Thymeleaf];
    • un proyecto en el que la aplicación web envía un flujo JSON al navegador;

    En el primer caso, el proyecto requiere dos dependencias de Maven:

    
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>1.1.9.RELEASE</version>
    </parent>
 
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-thymeleaf</artifactId>
        </dependency>
</dependencies>

    En el segundo caso, las dependencias de Maven son las siguientes:

    
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>1.1.9.RELEASE</version>
    </parent>
 
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
</dependencies>

    Estas configuraciones introducen un gran número de dependencias en cascada, muchas de las cuales son innecesarias. Para implementar la aplicación, utilizaremos una configuración manual de Maven que incluya solo las dependencias necesarias para el proyecto.

    Ahora volveremos a los fundamentos de la programación web introduciendo dos conceptos fundamentales:

    • el intercambio HTTP (Protocolo de Transferencia de Hipertexto) entre un navegador y una aplicación web;
    • el HTML (HyperText Markup Language) que el navegador interpreta para mostrar una página que ha recibido;
